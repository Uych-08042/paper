# Stage-157 固定加算次数下的写回对照

Stage-156 的低 Hann 峰值规则触发了 16 个起点，其中 14 个是失跟起点，2 个是稳定起点。本轮锁定这 16 个起点，判断看过 L9 和适配 L10 的输出以后，能否选对写入下一帧搜索状态的框。 [Stage-156 结果](STAGE156_DEPTH_ROUTING_AUDIT.md)

## 缓存结果

按视频平均，三组均以原生为参照。后续 IoU 使用 32 帧，不含起点。

| 策略 | 加算预算 | 实际写入 L10 框 | 后 32 帧 IoU 差 | 新增／丢失连续好框 | 新增连续低 IoU |
|---|---:|---:|---:|---:|---:|
| 原生 SGLA | 0 | 0 | 0 | 0／0 | 0 |
| 加算后直接写回 | 16 | 16 | −0.415 点 | 1／1 | 1 |
| 真值事后保护参考 | 16 | 9 | +0.203 点 | 1／0 | 0 |

事后参考选取后 32 帧 IoU 改善、同时保住原生单帧好框和连续恢复，且无新增连续低 IoU 的分支。它在 0348／367 保留原生框，在 0085／1541 写入适配框。相对直接写回改善 +0.618 点，以未来标签为依据，仅用于估计本批候选里可保留的收益。

## GPU 对照

复用 Stage-155 两折适配权重。每个触发起点用同一个模板、父框、裁剪、选择器和 L9 特征，分别解码 L9 和 L9 → 适配 L10。各自从同一时刻写回并续跑 32 帧，后继全部使用原生逻辑。原设备身份匹配时，核对两条分支和原始 L9 峰值与归档一致。换 L20 或另一 L40 时，16 个起点的两路同时重跑，报告该次硬件身份。

比较三种同预算规则：直接写回 L10、仅在 L10 的 Hann 峰值严格更高时写回、在峰值更高且两框 IoU ≥ 0.30 时写回。后者是固定保护阈值，用于检验明显冲突框对闭环的影响。否决时写回原生 L9 框。三条规则共享 16 次追加 L10、16 次额外 CENTER 调用。真实采集做 16 次共享裁剪和 1,024 次后继搜索。当前脚本记录调用次数，延迟和在线整段效果需另测。

## 复现

仅基于已归档 CSV 计算事后参考：

```bash
python -B tools/stage157_depth_writeback.py --cached-bound --output-dir output/stage157/cached_bound_v1
```

同步代码和归档结果后，在服务器仓库根目录后台运行 GPU 对照：

```bash
mkdir -p output/stage157
nohup bash tools/run_stage157_depth_writeback.sh > output/stage157/run_stage157.log 2>&1 < /dev/null &
```

默认输出为 `output/stage157/matched_writeback_v1/`。首次可用 L20 或 L40。续跑若换卡或换 GPU 实例，用新的 `STAGE157_ROOT` 保持同一结果目录的匹配关系。完成后回传 `stage157_results_*.txt`。
