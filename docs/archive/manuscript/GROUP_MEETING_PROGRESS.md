# 组会进展汇报提纲

## 建议题目

**从层自适应到效用感知：面向无人机跟踪的动态推理诊断与建模**

一句话结论：现有实验已经证明“额外计算是否有用”具有明显的逐帧差异，但固定深度、原始层选择器和简单置信度均不能稳定识别这种收益；下一阶段应转向基于因果特征的候选动作效用预测，并以闭环轨迹和真实时延验证。

## 汇报策略

不要按 Stage-1、Stage-2、Stage-3 顺序罗列脚本和运行过程。建议围绕三个问题展开：

1. 不同帧是否真的需要不同计算量？
2. 有价值的额外计算能否在执行前被识别？
3. 离线收益能否在真实闭环跟踪中保留下来？

整场汇报可以控制在 12 页、15--20 分钟。前 8 页讲已经得到的证据，后 4 页讲由证据推出的方法与下一步实验。

## 幻灯片结构

### 第 1 页：研究问题与当前判断

标题：**UAV 跟踪中的额外计算应该何时执行、执行哪一层？**

- 背景：Transformer 跟踪器通常具有固定或粗粒度计算路径，而 UAV 平台要求低时延。
- 原始设想：困难帧增加计算，简单帧走快速路径。
- 当前认识：真正需要预测的不是笼统的“困难度”，而是每个候选动作相对 Fast 路径的边际定位收益。

口头表述：

> 目前课题已经完成了可行性诊断。结果支持动态计算的必要性，但也否定了“置信度低就多算几层”这一过于简单的实现方式。

### 第 2 页：基线与受控实验设计

标题：**冻结模型，只改变推理动作**

- 基线：SGLATrack-DeiT*，checkpoint `ep0297`，UAV123 共 123 个序列。
- Fast：执行 L1--L6 后直接预测。
- SGLA：执行 L1--L6，再执行原选择器指定的一个候选层。
- Full：顺序执行 L1--L12。
- Independent candidates：将 L7--L12 分别独立作用于同一份 L6 token，每个候选独立预测。
- 第一阶段采用 shared-trajectory，后续增加每个策略自行更新状态的 closed-loop。

建议图：画一张主干 L1--L6 后分成 Fast、SGLA、Full 和六个独立候选的结构图。

### 第 3 页：发现一，深度增加不等于精度提高

标题：**顺序执行全部层反而降低性能**

| 路径 | UAV123 AUC |
|---|---:|
| Fast，L1--L6 | 66.2912 |
| SGLA，L1--L6 + selected | 66.5143 |
| Full，L1--L12 sequential | 63.7242 |

核心解释：

- SGLATrack 的后续层不是一个可以直接顺序加深的普通 backbone。
- “多计算”本身不是有效动作，计算路径的语义比层数更重要。
- 因此不能把课题简化为二分类的 Fast/Full 路由。

### 第 4 页：发现二，候选层存在明显互补性

标题：**最佳候选随帧变化，存在可利用的 Oracle 空间**

| 方法 | UAV123 AUC | 相对 Fast 增益 |
|---|---:|---:|
| 固定最佳层 L9 | 66.5143 | +0.2230 |
| 六候选中逐帧最佳 | 69.7411 | +3.4498 |
| Fast 与六候选中逐帧最佳动作 | 69.8518 | +3.5606 |

补充证据：L7--L12 均在相当比例的帧上成为最佳或并列最佳候选，并不存在一个全局最优层。

需要强调：Oracle 只用于证明上限与互补性，不是可部署方法，也不能作为最终性能结论。

建议图：候选层最佳比例柱状图，并在右侧放固定 L9 与 Oracle 的 AUC 对比。

### 第 5 页：发现三，原始选择器没有利用互补性

标题：**选择器在当前配置下退化为固定 L9**

- 原始 SGLA selector 在全部有效决策帧上均选择 L9。
- 对六候选逐帧最佳层的精确命中率为 27.55%。
- SGLA 相对 Fast 仅提升 0.2230 AUC，远低于候选 Oracle 的 3.4498 AUC。

结论：表示冗余或层相似度并不等价于候选层对当前定位任务的真实收益。

### 第 6 页：发现四，手工可观测特征预测能力弱

标题：**简单置信度和运动特征无法可靠预测收益**

| 模型 | Benefit AUROC | 说明 |
|---|---:|---|
| Ridge，28 个因果特征 | 0.4937 | 接近随机 |
| MLP，28 个因果特征 | 0.5088 | 接近随机 |

- Ridge 在 50% 深计算预算下仅达到 66.5573 AUC，相对 Fast 提升 0.2661。
- 同一预算下的候选 Oracle 为 69.4292，说明问题不是缺少潜在收益，而是现有特征没有表达出收益。
- 这一步排除了“用少量置信度和几何量训练一个轻量分类器即可”的简单路线。

### 第 7 页：发现五，shared-trajectory 会高估可部署结果

标题：**跟踪决策会改变未来输入，必须闭环验证**

| 策略 | Closed-loop AUC | 模型/解码时延 |
|---|---:|---:|
| Fast | 64.4089 | 4.367 ms |
| Median4 | 64.7181 | 9.791 ms |
| Median6 | 66.1426 | 13.353 ms |
| SGLA | 66.5143 | 待全量同步测量 |

- Fast 在 SGLA 共享轨迹上为 66.2912，但在自身轨迹中为 64.4089，下降 1.8824 AUC。
- Median6 虽接近 SGLA，但仍低 0.3717 AUC，且计算开销明显更大。
- 当前闭环结果说明：单帧反事实收益不能直接等价为真实跟踪收益。

建议图：左侧画 shared 与 closed-loop 的状态传播差异，右侧画 AUC--latency 散点图。

### 第 8 页：阶段性结论

标题：**已经确认什么，又排除了什么？**

已确认：

- 不同帧、不同候选动作的收益差异显著。
- 固定增加深度不是有效方案。
- 独立候选层具有可利用的互补上限。
- 闭环状态分布是方法设计和评估中的关键因素。

已排除或暂不支持：

- 顺序 Full 路径作为强模型。
- 原始 selector 直接承担效用路由。
- 仅依赖置信度和简单运动量的路由。
- 固定候选框融合替代动作选择。

### 第 9 页：由实验推出的简单建模

标题：**将动态推理建模为成本敏感的动作效用预测**

动作集合：

\[
\mathcal{A}_t=\{\text{Fast},L7,L8,L9,L10,L11,L12\}.
\]

候选层的监督效用：

\[
u_{t,k}=\operatorname{IoU}(b_{t,k},g_t)-\operatorname{IoU}(b_{t,F},g_t).
\]

成本敏感决策：

\[
a_t^*=\arg\max_{a\in\mathcal{A}_t}
\left[\widehat{u}_{t,a}-\lambda c_a\right].
\]

其中路由器只能使用执行候选层之前可获得的信息：L6 全通道特征、Fast response、历史运动和历史置信状态。Ground truth 只生成训练标签，不进入输入。

### 第 10 页：下一阶段实验闭环

标题：**Stage-4：训练真正的 utility-aware router**

1. 在 GOT-10k 或 LaSOT 训练集上采集 Fast 与 SGLA rollout 的状态。
2. 对同一状态离线执行 L7--L12，生成各动作效用标签。
3. 训练共享编码器加七动作效用头，同时加入成本正则。
4. 在不重叠的视频上调参，禁止使用 UAV123 测试标签训练路由器。
5. 在 UAV123 上做 closed-loop 测试，并同步测量 GPU 时延。
6. 输出完整 accuracy--latency Pareto 曲线，而不是只报告单个 AUC。

### 第 11 页：成功标准与必要消融

标题：**什么结果才算方法成立？**

最低成功标准：

- 在 closed-loop 下明显优于 Fast。
- 在相近 AUC 下低于 SGLA 的平均计算开销，或在相近开销下高于 SGLA。
- 改变成本系数后形成稳定、单调的精度--时延曲线。
- 收益在不同序列属性或第二个测试集上仍存在。

必要消融：

- L6 pooled feature、Fast response、temporal state 各自贡献。
- 只预测是否 deep，与联合预测具体候选层的差异。
- Fast rollout、SGLA rollout 和混合 rollout 的训练差异。
- 分类目标、效用回归目标和排序目标的差异。
- 不同候选子集带来的性能与计算折中。

### 第 12 页：风险、当前缺口与组会希望讨论的问题

标题：**下一步需要做出的三个决定**

- 方法风险：候选收益可能高度依赖当前轨迹，单步监督未必能学习长期价值。
- 工程风险：六候选标签采集成本较高，需要先用较小训练子集验证可学性。
- 论文风险：如果路由器只能恢复很少 Oracle 空间，贡献应转向闭环评估协议与诊断，而不能夸大方法性能。

建议向导师明确请教：

1. 论文定位更偏视觉跟踪方法，还是边缘计算/资源调度？
2. 首轮训练优先使用 GOT-10k 还是 LaSOT，数据规模和远程算力预算如何安排？
3. 达到何种 accuracy--latency 改善后，再扩展到网络状态与 offloading？

## 当前完成度的客观表述

- **问题验证：较充分。** 已经建立从路径分解、Oracle 上限、可学习性诊断到闭环验证的证据链。
- **方法实现：尚处于前期。** utility-aware router 仍需正式训练和闭环测试，现阶段不能宣称方法有效。
- **实验系统：主体已搭好。** 已具备候选数据采集、离线分析和闭环评估基础；校正后的融合指标、全量同步 profiling 和训练缓存仍需在远程运行。
- **论文写作：框架已经形成。** Introduction 可以继续打磨，Related Work、Problem Formulation 和 Experimental Protocol 可以开始；Abstract、最终方法贡献和主结果表应等待 Stage-4C。

## 汇报时应避免的表述

- 不说“我们的方法已经提高了 3.56 AUC”；3.56 是使用 ground truth 的 Oracle 上限。
- 不把 shared-trajectory AUC 当作最终部署结果。
- 不把旧的离线融合结果作为正式结论，修正指标后需重新运行。
- 不把当前工作描述成已经实现边缘卸载；目前证据只支持本地动态计算建模。
- 不用大量脚本名称和 CSV 路径占据正文，放到备份页即可。

## 推荐收尾

> 当前阶段最重要的结果不是得到了一条已经优于基线的策略，而是把问题从“困难帧是否要多算”收敛成了“如何在闭环状态下预测各计算动作的边际效用”。已有实验同时证明了可利用的性能空间和现有启发式信号的不足。下一步将用独立训练数据学习动作效用，并以闭环精度--时延曲线判断该方向能否形成完整方法论文。
