# Stage-154 强制加算一块的同裁剪对照

Stage-153 的难帧规则未触发加算。Stage-154 在同一个搜索裁剪上对比原生路径和强制串行加一块，直接测量框的变化及其对后续跟踪的影响。 [Stage-153 结果](STAGE153_RESULTS_REVIEW.md)

## 实验设计

- 沿用 Stage-134 和 Stage-137 的 47 个配对起点，包含 19 个失跟起点和 28 个稳定起点。失跟组另按原生响应网格中是否有好框记录。
- 起始帧共用图像、模板、父框和裁剪。两组的裁剪像素哈希须与原缓存一致。原生组按原选择器执行一个后段块，加算组在该块后串行执行下一块。例如选 L9 时，两组后段分别是 L9 和 L9 → L10。若更换运行身份后有起点实际选到 L12，该点的追加不可用，表中单独记录。
- 两组沿用同一 checkpoint、预测头和 Hann 解码。每路每帧只调用一次裁剪、选择器和预测头。两组将各自的起始帧预测框写回，此后均用原生路径续跑 32 帧。整轮计划执行 3,102 次搜索，实际附加块数会从调用记录核对。
- 报告起点 IoU、IoU ≥ 0.50 的框新增与损失、后继 8／32 帧的平均 IoU、连续三帧好框、连续三帧严重低 IoU（IoU < 0.20）。配对汇总先在每段视频内平均，再跨视频等权。与 Stage-134 运行身份相同时，核对原生分支的预测框和被选块。

这是开发集起点上的一次加算干预。它估计追加块在相同裁剪上的实际输出变化，以及一次写回后的短程影响。

## 执行

同步代码后，在训练服务器仓库根目录的 `sglatrack-test` 环境运行。需要原 SGLA 权重、VisDrone-SOT 图像及 Stage-76、89、93、134、137 的完整产物。首次选择 L20 或 L40，同次两组在同一卡比较。换卡后续跑使用新的 `STAGE154_ROOT`。

```bash
mkdir -p output/stage154
nohup bash tools/run_stage154_forced_depth.sh > output/stage154/run_stage154.log 2>&1 < /dev/null &
```

默认输出至 `output/stage154/forced_serial_depth_v1/`，完成后回传其中的 `stage154_results_*.txt`。
