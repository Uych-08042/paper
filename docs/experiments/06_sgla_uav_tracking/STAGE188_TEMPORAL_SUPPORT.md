# Stage-188 补充开发源组与历史位置对照

Stage-187 的 15 个完整事件窗只有 3 个安全挽救机会。最高 Hann 和裁剪一致性各选中 2 个，一致性多造成 1 次事件伤害。Stage-188 扩充源组，同时检验过去帧的位置能否为同帧候选排序提供额外证据。

## 样本与对照

- 比较 Stage-79 封存名册和 Stage-93／170 的 28 个近期开发源组。封存名册排除的 40 个历史开发源组中，有 12 个没有参加近期对照。每组优先选满足长度要求的最长序列，同长度按序列名排序。12 是候选源组数，实际支持由报告列出。
- 每个入选视频先跑原生 SGLA。取有足够因果历史和后续 128 帧的第一个原生失跟起点。另取一个与失跟窗互不重叠、历史及后续 IoU 均至少为 0.5 的稳定窗口。真值只用于离线选点与评估。Stage-79 封存源组仅核对名册及目录清单，图像和标注内容不进入本轮。
- 以当前父框和更早一帧的原生预测中心构造等尺寸邻域。复用 Stage-186 的取整和方向规则，保留不同的物理裁剪，每个送同一个 L9 与 CENTER＋Hann。这个邻域的位移来自原生历史。Stage-187 的位移来自已归档的写回干预，故本轮各组均值单独报告。
- 四条规则共用完全相同的候选和搜索预算。三条对照为当前裁剪、最高 Hann、裁剪一致性。`history_position` 取最近 16 个原生预测中心的逐轴位移中位数，用上一个中心加这个位移预测当前位置，再从候选预测框中选中心最近的一个。16 帧为沿用的固定诊断参数。这轮只测位置，不训练、不调参。
- 在测试帧写回候选输出后，后续 128 帧回到各自轨迹的原生搜索与原生选层。跟原生轨迹比较后效、事件伤害和安全挽救。安全挽救使用 Stage-183 的冻结事件定义。

## 结果判读

先读 `stage188_support.csv` 和 `stage188_summary.csv`，确认有效事件窗、稳定窗及安全挽救供给。再读 `stage188_paired.csv` 的 `history_position` 对 `highest_hann`，关注选择变化、新增与丢失的挽救、新增与移除的伤害、按源组平均后效及去除最佳源组后的后效。即使历史位置占优，这也是历史接触过的开发源组上的局部续跑证据。供给稀少时，报告缺少判别样本。

若多个源组有挽救增量且稳定窗没有新增伤害，下一轮复验顺序和完整视频后效。若已有足够可挽救候选，而历史位置仍无法辨别，再在同一候选池对照跨帧外观。若候选池缺少可挽救框，优先复查候选供给。

## 运行

在已有 Stage-76、89、93、170、187 结果和原始 SGLA 权重的服务器仓库执行。脚本支持 L20 和 L40，运行与续跑绑定实际 GPU 和软件身份。运行日志按固定间隔刷新总体进度。

```bash
mkdir -p output/stage188
nohup bash tools/run_stage188_temporal_support.sh > output/stage188/run.log 2>&1 &
tail -f output/stage188/run.log
```

成功后脚本打印 `output/stage188/temporal_support_v1` 下的 `stage188_results_*.txt` 路径。

## 结果

已核验 2026-11-24 回传的决策指纹和六张 CSV 哈希，并从候选表核对 44 次选择的目标分数、复算汇总与配对结果。服务器运行在 NVIDIA L20，决策指纹为 `1c030e7fcec60b73aeefe900ed8310e10ebdabd86b5c68e574131c4eb022e8d8`。本地复核使用回传文本，未重读服务器上的图像和轨迹 NPZ。

12 个候选源组中，10 个序列进入原生跟踪，共 11,470 帧。`0001` 和 `0002` 未进入本轮选定序列。原生共出现 3 次失跟，其中 `0107`、`0173` 有符合条件的完整事件窗，`0331` 只进入稳定对照。最终有 2 个完整事件窗、9 个稳定窗和 43 个去重裁剪。确认源组未打开。

| 窗口 | 历史位置相对最高 Hann 的后 128 帧平均 IoU | 源组胜／平／负 | 新增事件伤害 |
| --- | ---: | ---: | ---: |
| 失跟起点（2） | −0.00317 | 1／0／1 | 0 |
| 稳定对照（9） | −0.00020 | 1／5／3 | 0 |

两个失跟起点的候选池均无安全挽救，四条规则选中的安全挽救也均为 0。历史位置在两个失跟点均改选了其他候选，这个样本仍无法评估它识别安全挽救候选的能力。

- `0107:161` 只有两个不同裁剪。当帧最高 IoU 为 0.198，任何候选都没有给出可用的高重叠框。候选中最好的后 128 帧平均 IoU 增量为 +0.00127。
- `0173:502` 有六个不同裁剪。当前框 IoU 0.072，最高 Hann 选到 0.860，历史位置选到 0.837。两者后 128 帧相对原生的平均 IoU 分别增加 0.02389 和 0.01629，均未达到安全挽救的事件标准。此例说明当帧纠正可以发生，后续能维持多久需逐帧核查。

## 下一轮建议

先对已保存的候选续跑做逐帧核查。用 `0173:502` 的原生、最高 Hann、历史位置三条轨迹，定位当帧纠正后首次进入低 IoU、恢复和再次失跟的位置，并报告改善持续时长。将 `0107:161` 作为当帧候选不足的对照。同一分析可把 `0331` 的原生失跟作为受现有跟踪长度或窗口资格限制的个案，先核实为何未入选，再决定是否另报可观测长度。若核查显示高 IoU 写回很快丢失，后续对照应聚焦写回后的搜索状态；若主要缺少当帧好框，再检验搜索范围与裁剪内候选的供给。
